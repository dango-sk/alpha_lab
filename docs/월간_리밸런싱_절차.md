# 월간 리밸런싱 절차

매달 말 실행하는 순서. 2026-08-31(9월 리밸) 작업에서 겪은 사고를 반영해 정리했다.

---

## 0. 전제 — LG그램에서 PG 업로드 (수동, 선행 필수)

`run_pipeline`은 주가를 올리지 않는다. **월말 종가·시총·수급을 Railway PG에 먼저 올려야** 한다.

| 테이블 | 내용 |
|---|---|
| `daily_price` | 일봉 (종가·시총) |
| `macro_indicators` 의 `investor_*` | 외국인·기관·개인 수급 |

업로드 안 하면 파이프라인이 **직전 영업일 기준으로 조용히 계산**한다. 에러가 안 나므로 반드시 확인할 것.

---

## 1. 지난달 확정본 freeze (아직 안 했다면)

```bash
cd ~/Desktop/alpha_lab
```

freeze 안 하면 1일이 휴일인 달에 **리밸이 2개로 늘어난다.**
(예: 8/1 토요일 → 8월 데이터 도착 시 실제 첫거래일 8/3이 중복 생성)

## 2. prefetch 캐시 삭제 ★ 빠뜨리기 쉬움

```bash
rm -rf cache/prefetch
```

이 캐시는 신선도를 **`daily_price`의 MAX(trade_date)만 보고** 판단한다
([factor_engine.py:262](../lib/factor_engine.py#L262)).
forward·consensus·재무를 새로 받아도 주가 날짜가 그대로면 **옛 캐시를 그대로 재사용**한다.

> 2026-08-29 사고: 이걸 안 지워서 30종목짜리 낡은 forward로 9월 포트폴리오가 잘못 계산됨.

## 4. 검증 — 3가지

### 4-1. 데이터 신선도

```bash
.venv/bin/python scripts/check_freshness.py
```

`macro_indicators`, `technical_indicators`, `daily_price`가 월말까지 왔는지 확인.
❌가 하나라도 있으면 레짐 예측이 낡은 값으로 돌아간 것이니 중단.

### 4-2. forward 수집량 ★ 이번에 문제됐던 부분

```sql
SELECT trade_date, COUNT(*) FROM alpha_lab.fnspace_forward
WHERE trade_date >= '2026-08-20' GROUP BY 1 ORDER BY 1;
```

**정상은 440~460종목.** 300 이하면 수집이 끊긴 것이다.

네트워크가 끊기면 파이프라인이 그 단계만 실패하고 **나머지는 그냥 진행**하므로,
종목 수를 직접 세어봐야 한다. 결손 시 재수집:

```bash
.venv/bin/python -c "
import sys; sys.path.insert(0,'scripts')
from run_pipeline import step_collect_forward, step_collect_consensus_daily
step_collect_forward('20260826'); step_collect_consensus_daily('20260826')"
```

### 4-3. 점수 분포

```bash
.venv/bin/python -c "
import sys; sys.path.insert(0,'.')
from lib.data import _load_holdings_cache
c=_load_holdings_cache('KOSPI','monthly')['레짐조합_FCF_YIELD추가전략↑_FCF_YIELD_BEAR전략↓']
```

## 5. 종목 확인 후 확정 — 2단계 모두 필요

### 5-1. 유니버스 freeze

```bash
.venv/bin/python scripts/step6_build_universe.py --freeze 2026-09-01
.venv/bin/python scripts/step6_build_universe.py --list-frozen   # 확인
```

### 5-2. 확정본 pin ★ 8월에 빠뜨려서 기록이 사라진 단계

```bash
.venv/bin/python - <<'EOF'
import os, sys, json, psycopg2
sys.path.insert(0, '.')
from dotenv import load_dotenv; load_dotenv()
from lib.data import _load_holdings_cache

NAME = '레짐조합_FCF_YIELD추가전략↑_FCF_YIELD_BEAR전략↓'
DATE = '2026-09-01'
NOTE = '9월 확정본. 파이프라인 재실행 시 이 값으로 복원.'
EXCLUDE = []          # 예: ['034230']  빼라고 지시받은 종목
rows = _load_holdings_cache('KOSPI', 'monthly')[NAME][DATE]
rows = [r for r in rows if r[0] not in EXCLUDE]
tot = sum(r[2] for r in rows)
rows = [[r[0], r[1], r[2]/tot, r[3]] for r in rows]      # 비중 재정규화

conn = psycopg2.connect(os.environ['DATABASE_URL']); cur = conn.cursor()
cur.execute("""INSERT INTO alpha_lab.holdings_pin
               (name, universe, rebal_type, rebal_date, rows_json, note, created_at)
               VALUES (%s,'KOSPI','monthly',%s,%s,%s, NOW())""",
            (NAME, DATE, json.dumps(rows), NOTE))
conn.commit()
print(f'✅ pin 저장: {DATE} {len(rows)}종목, 비중합 {sum(r[2] for r in rows):.4f}')
EOF
```

### 왜 둘 다 필요한가

| | 지키는 대상 | 안 하면 |
|---|---|---|
| `universe_frozen` (freeze) | 후보군 (약 450종목) | 리밸 날짜가 중복 생성됨 |
| `holdings_pin` (pin) | **최종 30종목 + 비중** | 재실행 때마다 종목이 바뀜 |

**freeze만으로는 부족하다.** freeze는 후보군만 고정하고,
`step7_backtest.py`는 freeze를 보지 않고 **모든 리밸의 점수를 다시 계산**한다.
재무·TTM 데이터가 갱신되면 과거 리밸의 최종 종목까지 바뀐다.

> 2026-08 사고: 8/1을 freeze했지만 pin을 안 해서, 재실행 후 8월 포트폴리오에서
> 기아(29.6%)가 사라짐. 원래 보유 종목 기록이 DB에 남지 않았다.
